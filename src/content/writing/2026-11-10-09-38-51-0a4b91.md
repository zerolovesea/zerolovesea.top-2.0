最近把言录的ui做了一次彻底的推翻设计，版本号也从v1.4.5直接来到了v2.0.0。官网也做了重新设计，不过如果仅仅是ui上的更新，那还算不上是大版本更新，更重要的是背后对架构的重新设计。

## 新功能

首先看看新增了什么主要功能：

- 纪要溯源：从纪要结论、原因图跳转到对应逐字稿和录音。

这个功能主要是对会议纪要和转录文字的关联，让ai输出的纪要有实际的原文作为参考，避免ai幻觉带来会议纪要胡编乱造。

![](/_posts/2026-11-10-09-38-51-0a4b91/093ffb40-16bb-42a5-8223-f2df57444225.png)

- 术语库：ai根据转写的内容，判断哪些是可能存在识别错误的专业术语，记录成长期记忆，从而优化会议纪要的质量。

![](/_posts/2026-11-10-09-38-51-0a4b91/image.png)

- 按说话人回看：从参与者列表、逐字稿头像或段落菜单筛选某人的发言，并支持整场改名。这个功能来自github issue区用户提出的建议，我觉得很不错。

![](/_posts/2026-11-10-09-38-51-0a4b91/16b15e9e-e0c7-45eb-adb7-235b7c86ae27.png)

- 本机 Agent 接入：通过 CLI、MCP 查询会议、控制录音、转写文件、翻译字幕、查询和取消任务。这个功能来自朋友的建议，也比较契合原生ai工具的逻辑。外部 Agent 可以查询会议、列出模型和设备、控制录音、执行转写、翻译字幕及查询或取消任务。字幕翻译保留时间轴

![](/_posts/2026-11-10-09-38-51-0a4b91/fdbedab2-e5a5-4656-a361-1a30d07292ae.png)

- 后台录音提醒：检测支持的会议应用发声并提醒开始录音，支持添加本机会议客户端。这个主意来自一个商业会议转写应用，它能检测到电脑里有会议应用发声时，自动弹窗让用户快速记录。
- 全局录音快捷键：无需切回主窗口即可控制录音，使用快捷键一键快速会议。
- 胶囊回放功能：增加录音回放控制、整场字幕滚动，以及展开编辑笔记、粘贴图片。会议胶囊现在支持更多场景了。

![](/_posts/2026-11-10-09-38-51-0a4b91/bea97cdc-db0e-4c83-9ceb-dfdb67776094.png)

## 架构改进

架构上，言录抛弃了之前的Electron+python路线，原因是太重了，打包完就要220mb，如果加上转写模型和其他组件，光是使用一个应用就要超过1个g，这甚至还没算录音。因此我参考了一些高分的项目，改成了Tauri+Rust，其中macOS和Windows分别用 WKWebView以及WebView2进行渲染。后端逻辑和推理逻辑改成了Node.js和C++版本的 sherpa onnx / llama.cpp以及Swift MLX / Metal。用astra高级别跑了一轮，再微调几次就差不多完成了迁移，应用不再打包 Electron、Python、FFmpeg后，效果很显著：现在安装包只有40-50mb，这还是包含了vad，标点符号等小模型的情况下。转写速度上也有一定的提升，测试转写一段66分钟的录音，在我的m4 pro 24g上转写大致花了3分半钟。

## 后端统一的探索

尽管架构上做了大量探索，但是Windows与macOS（macos之所以没用sherpa，是因为Apple Silicon上，mlx实测的推理性能更好）的现在还是独立的架构，windows用sherpa onnx cpu作为后端，这导致几个问题：

1. 性能对比macos版本后端mlx audio差距很大，用不上cuda加速
2. sherpa和mlx的模型支持不一样，导致两个平台的模型清单不一致
3. 代码不统一，导致维护起来要分开维护

另一方面我还想用上vulkan这类加速后端，因此需要一套跨平台的推理实现。

我探索了一下同类的开源高分实现，发现支持跨平台的高分项目，抛开用sherpa-onnx或者fun-asr的项目，有几类：

- 一类只用whisper.cpp，这类应用只适配whisper类的模型
- 一类用transcribe-cpp，然后针对不同模型族选择不同的引擎

由于我需要支持不同架构的模型，因此我尝试同一模型用 C++/MLX 实现，然后按设备跑不同后端。这样的好处是权重可以用一个，而且一个模型的推理逻辑不用在三个平台写三遍。

用fun asr模型做了三端测试，结果并没有达到预期：

![](/_posts/2026-11-10-09-38-51-0a4b91/a64057ec-c573-4114-9824-8182296c031f.png)

可以看到在windows上，性能出现了回退，可能是cpu太弱了。gpt的解释是代码在CPU上把量化矩阵展开成 FP32，每个权重从1字节变为了4字节，每次转写用了体积更大的矩阵。而模型又是逐个生成token，每生成一个 token 都要经过多层投影，因此读取权重的成本会反复出现，而onnx的实现直接用量化模型，节省了矩阵计算的成本。

虽然有优化方向，但是考虑到之后的模型扩展性，如果每个模型都要定制化代码的话，维护起来有点麻烦，所以我最后还是选择通用实现，macos/linux使用mlx，windows继续使用sherpa-onnx，并且分别编译了各自的cuda版本。

## 关于踩了哪些坑

照例总结整理一下开发周期中遇到的坑：

1. 原生平台的行为差异

Windows 上连续出现 Unicode 路径、普通路径与特殊路径形式、ZIP64、NSIS 插件执行时机、ACL、WebView2 测试窗口、进程退出和旧安装目录的问题，跨平台的工作量比想象的要多。

2. 透明窗口与 WebView 绘制不同步

在会议胶囊这个feature上，出现过很多bug：关闭时闪烁、字幕不完整、缩放不稳定、旧像素消失、透明区域截获点击等。问题在于 AppKit 改完窗口尺寸，不代表 WebKit 已画完新尺寸，当出现超时的时候，就会持续闪烁。

3. 模型的推理和性能

Windows Nano 量化路径、CPU 兼容和真实推理验证，引出了多次诊断与 CI 调整。会议纪要也暴露出很多的模型问题：上下文不足、输出截断、摘要没有变短、反复归并不收敛、遗漏行动和数字、错误归类原因。

4. 异步结果覆盖用户状态

会话切换、后台翻译、手机快照、说话人改绑、笔记编辑、重复建议采纳、撤销信任，都遇到了类似问题，后台任务的生命周期比界面状态更长，就会导致用户操作后，界面却返回了原始状态。


先写到这，截至11月18日，版本更新到了2.1.2，目前的体验相对完整，暂时没有出现体验上的bug，cuda版本测试也没有问题。不过一些用户反馈会议纪要的质量和钉钉飞书这些竞品还有差距，这点还需要持续优化。
